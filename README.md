# Woodline · ежедневная рабочая доска

Мебельный e-commerce: цикл 1 ноября 2026 — 28 февраля 2027. Округлённый исходный ориентир 400 млн сум в месяц; цель **декабря** — 800 млн, stretch 1,2 млрд. Январь и февраль — низкий сезон, числовой план не выдумывается.

## Запуск

Node.js 22+, без серверных npm-зависимостей:

```sh
npm start
npm test
```

Сервер слушает `0.0.0.0`, `PORT` (по умолчанию 3000). `/health` — проверка работоспособности. GitHub Pages раздаёт те же статические файлы напрямую, Node для Pages не нужен. Railway использует Dockerfile.

## Что хранится и где

- Без входа: локальная доска конкретного браузера, без синхронизации с телефоном.
- После входа: одна приватная доска на аккаунт Supabase. Используйте один email на своих устройствах. Другие аккаунты имеют отдельные доски, совместные роли сотрудников пока не реализованы.
- Локальная очередь сохраняет изменения до отправки. Статус «Сохранено в облаке» появляется только после подтверждения сервера. При конфликте целых версий пользователь выбирает нужную; автоматического слияния нет.
- Первое заполнение облака — только явной кнопкой. Анонимная доска никогда не отправляется автоматически.
- Устройства должны быть доверенными: сессия и приватные офлайн-копии аккаунта хранятся в браузере. Выход из аккаунта скрывает данные, но не стирает его очередь/архив.
- История облачных версий ограничена последними 50 снимками. JSON-экспорт — независимая резервная копия; это не обещание вечного хранения. Бесплатный Supabase имеет квоты и может приостанавливать неактивные проекты.

## Подключение реальной базы

См. [supabase/README.md](supabase/README.md) и [supabase/schema.sql](supabase/schema.sql).

1. Владелец создаёт бесплатный Supabase-проект в своём аккаунте.
2. В SQL Editor выполняет `supabase/schema.sql`: закрытые RLS-таблицы, compare-and-swap RPC, приватная история версий.
3. В Auth → URL Configuration задаёт URL сайта и разрешённые redirect URL (включая GitHub Pages с `/woodline-board/`). Email confirmation и reset проверяются реальными письмами; стандартный почтовый сервис Supabase имеет ограничения.
4. Публичные Project URL и publishable/anon key задаются в `app-config.js` для всех устройств. Допустима локальная настройка через окно входа, но её придётся повторить на телефоне. **Secret/service_role ключи и пароль БД нельзя помещать в браузер или репозиторий.**
5. Создаёт аккаунт, подтверждает email, входит и явно загружает локальную доску. На телефоне входит тем же аккаунтом.
6. Проверяет: правка на ПК появляется на телефоне; правка с телефона — на ПК; офлайн-изменение дожидается сети; разные аккаунты не читают чужую доску.

Без этих действий проект работает локально. Наличие готового клиентского кода не означает, что живая облачная база уже создана.

## Аналитика

Финансовые факты отделены от задач. Журнал: одна дата × один канал, без повторного общего итога за тот же день. Неизвестное = пустое поле, подтверждённый ноль = `0`.

- Выручка и выполненные заказы — по дате исполнения.
- Прибыль — после согласованного набора расходов, в тех же единицах, что выручка.
- Отмены — отменённые заказы из когорты заказов, созданных в дату записи / все заказы той когорты. Запись обновляется по мере появления фактов.
- Просрочки — заказы с обещанной датой доставки в дату записи, исполненные с опозданием / все заказы с этой обещанной датой.
- Маржа и доля рекламы рассчитываются только по записям, где указаны оба сравниваемых показателя; неполные данные не считаются нулём.
- Недельные и месячные итоги рассчитываются из одних и тех же датированных фактов. Последняя неделя — 8 дней. Нет линейного прогноза декабря по одному дню или сравнения всего цикла с месячной целью.
- Прогресс задач показывает выполнение работы, не достижение цели выручки.

## Совместимость и сохранение старого прогресса

Старый ключ `woodline-growth-v1` не изменяется. При первом запуске он переносится в `woodline-workspace-v2` с сохранением задач, заметок, датированных результатов и исходного JSON. Старые ручные недельные итоги доступны отдельно и не складываются с дневными фактами: нельзя автоматически распределить неделю по месяцам и исключить дубли. Неповреждённый экспорт прежней версии можно импортировать.

Новый сезонный план не заменяет пользовательские задачи автоматически. Его можно добавить из вкладки «План и ориентиры»; задачи и сроки редактируются. Старый сайт в другом origin/браузере нужно сначала экспортировать, затем импортировать по новому адресу.

## Структура

- `board-model.js`: валидация, миграция и расчёты.
- `app.js`: интерфейс и редактирование.
- `cloud-sync.js`: Supabase Auth, локальная очередь и синхронизация.
- `plan-data.js`: сезонный план и инструкции к задачам; `plan-notes.md`: принятые допущения.
- `dashboard.css`: адаптивный интерфейс без CDN и внешних шрифтов.

Тесты модели и синхронизации не заменяют проверку реального Supabase, настроек Auth, квот и доставляемости писем.

### Автоматическое создание проекта владельца

Если владелец предоставляет `SUPABASE_ACCESS_TOKEN` через защищённые настройки среды, агент может выполнить `python scripts/provision-supabase.py`. Скрипт использует официальную Management API: создаёт/переиспользует отдельную организацию Woodline Free, проверяет тариф free, создаёт проект, применяет схему, проверяет RLS/запрет прямых записей и готовит публичный `app-config.js`. Существующие redirect URL сохраняются; подтверждение email не отключается. Пароль БД генерируется, не выводится и не сохраняется: при необходимости владелец сбросит его в Supabase. Сам management token в код не попадает.

Скрипт проверен с подставным API; реальное создание возможно только с рабочей авторизацией. Тест: `python -m unittest discover -s tests -p '*_test.py'`.

Приватная историческая база сравнения может импортироваться отдельным JSON `{kind:"woodline-baseline",baseline:{month,currency,channels:[{channel,values}],note}}`. Такой импорт меняет только базу сравнения, сохраняя задачи и дневной журнал. Реальные финансовые данные не следует добавлять в публичные исходники `plan-data.js`.

## Офлайн и обновления

После первого успешного открытия service worker сохраняет только приложение (7 статических файлов), без API/Auth-ответов. Уже открытая облачная доска использует отдельный приватный кэш аккаунта и очередь. Первая загрузка нового устройства всё равно требует сети; очистка данных браузера удаляет локальные копии.

Перед каждым изменением приложения для публикации выполните `npm run prepare:publish`: версия оболочки определяется содержимым файлов. Новый worker ждёт явного нажатия «Обновить», не перезагружает открытые формы автоматически. Сбой загрузки нового bundle оставляет предыдущую версию. При частичном удалении кэша нужен интернет для атомарного восстановления файлов. `scripts/provision-supabase.py` обновляет версию оболочки после записи публичной конфигурации проекта.

Если проект уже создан, используйте **project-scoped** токен и команду:

```sh
python scripts/provision-supabase.py --project-ref YOUR_20_LETTER_PROJECT_REF
```

В этом режиме скрипт не перечисляет организации, не проверяет чужие проекты и не создаёт новые ресурсы. Нужны Project Settings: Read, Database: Read and write, Auth Config: Read and write, API Keys: Read. Значения секретных API-ключей не запрашиваются и в браузер не записываются.
